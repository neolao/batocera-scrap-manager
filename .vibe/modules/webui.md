# Module: webui
**Role:** Serves the registry over HTTP — a summary of its systems, one paginated list of games per system, one page per game with its full metadata and media, the form correcting a game's metadata, the page confirming a game's deletion, one page per long operation on the ROMs folders (importing them into the registry, completing them from it), a themed error page, and the media files themselves.
**Files:** `internal/webui/webui.go`, `internal/webui/system.go`, `internal/webui/edit.go`, `internal/webui/save.go`, `internal/webui/rompath.go`, `internal/webui/protect.go`, `internal/webui/delete.go`, `internal/webui/job.go`, `internal/webui/import.go`, `internal/webui/complete.go`, `internal/webui/page.css`
**Exports:**
- `webui.Handler(reg *registry.Registry, registryFolder string, romsFolders []string) http.Handler` — the whole served site as a single `http.ServeMux`. `reg` is the served snapshot: it is never reloaded from disk (the registry is read once, when [`modules/cli.md`](cli.md)'s `serve` command starts), but a change made through the web UI — a correction, a deletion, an import — replaces it, so the result shows immediately while an external `update` still needs a restart. Requests are served concurrently, so a `sync.RWMutex` guards every access to it — the read handlers as much as the writers. `romsFolders` is the configured list the import reads and the completion writes back to; it is fixed for the process's lifetime and therefore needs no guarding, and an empty one is a valid state the pages word rather than an error.

**Depends on:** [`modules/registry.md`](registry.md), [`modules/site.md`](site.md), [`modules/store.md`](store.md)

## Routes
- `GET /` (exact, via the `/{$}` pattern) — the registry's summary, preceded by a `Maintenance` heading gathering the two long operations, each named by the **direction** it goes with a one-line note under its control (`homeView.Configured` gates them: with no ROMs folder neither is offered, and the sentence naming `config add-roms-folder` replaces both — a button leading to a dead end is worse). That block sits **outside** the "is the registry empty" branch, since an empty registry is precisely when importing matters most. Then: each system, sorted by name, with its game count and a link to its list. It names **no game**: rendering the whole registry here is what made the page unusable on a phone and expensive to serve (see [`decisions/023`](../decisions/023-system-pages-with-pagination-replace-the-single-game-list.md)). `systemSummaries` counts entries directly rather than going through `site.GroupBySystem`, so the page touches the disk not at all. It also renders the deletion banner (`homeView.Deleted`, `id="deleted"`) for the deletion that emptied its own system — hence one of the two read handlers taking the `*http.Request`. An empty registry renders the same page with a "No games in the registry yet." message rather than a blank body.
- `GET /system/{system}` — one page of that system's games (`gamesPerPage` = 60): breadcrumb, the system navigation bar (links now real URLs, the current one carrying `aria-current="page"`), a pager above and below the grid, one card per game linking to its own page, and the deletion banner when a deletion landed here. Cards carry `loading="lazy"` cover art and never embed a `<video>`. `entriesOfSystem` filters and sorts by game name — the very order `site.GroupBySystem` uses — so a page can be sliced *before* grouping, and only the sixty rendered entries have their media looked up on disk. The page is read from `?page=N`, absent meaning the first; an unknown system, and a page number that is not an integer in `[1, pageCount]`, both render the themed 404 rather than an empty list. Page 1 is addressed without the parameter (one canonical URL) but `?page=1` is accepted as-is. The pager is omitted entirely for a system fitting on one page.
- `GET /game/{system}/{id}` — one game's page: breadcrumb (`/`, then `/system/<system>`), the ROM path under the title (`gameDetail.RomPath`, rendered as `.game__file` — **not** a seventh `<dl>` row: that block carries a `hand-edited` badge slot per row, which is meaningless for an identity), cover art or a labelled "No cover art" placeholder, description or "No description available.", a `<dl>` of the six metadata labels (Rating, Year, Developer, Publisher, Genre, Players) whose rows are **always** rendered — an empty value shows a dash, so the label set stays identical from one game to the next — and a media section listing the video, marquee and thumbnail actually present on disk. `{id}` is a `registry.GameID`, resolved through `(*Registry).FindByID`; an unknown system, an unknown game, or a game requested under the wrong system all fall through to the not-found page.
- `GET /game/{system}/{id}/edit` — the pre-filled form correcting that game's metadata: a `ROM file` fieldset holding the path control alone, then one control per editable field, in the order the read-only page lists them, plus a "hand-edited" mark and a hand-back checkbox on every field the entry protects. Unknown game → the same themed 404.
- `POST /game/{system}/{id}/edit` — saves the correction, then `303 See Other` to `/game/{system}/{id}?saved=1#saved` (or `saved=stale-site` when only the site regeneration failed). A correction that changed the ROM path redirects to the game's **new** URL with `saved=path` (`path-stale` when only the site failed) plus the parameters composing its confirmation — see "Correcting the ROM path" below. Refusals: `403` for a submission that did not come from the registry's own pages, `400` for a body over `maxFormBytes` (64 KiB) or unreadable, `404` for an unknown game, `422` re-rendering the form with the submitted values plus per-field messages, `500` re-rendering it with a page-level `Problem` when the registry could not be written.
- `POST /game/{system}/{id}/protect` — protects the game as a whole or lifts that protection, then `303 See Other` to `/game/{system}/{id}?saved=protected|unprotected#saved` (suffixed with `-stale` when only the site regeneration failed). The submission carries the **desired end state** (`protected=on|off`), never "flip it", so a page rendered before the state changed elsewhere submits a harmless repeat instead of the opposite of what its button offered. Refusals: `403` cross-site (same `crossSite` check as the save), `400` for a missing or unrecognized state — never silently defaulted — `404` for an unknown game, `500` for a registry that could not be written, all leaving the served snapshot and the disk agreeing.
- `/game/{system}/{id}/protect` (methodless pattern) — any other method gets `405` with `Allow: POST`; it needs its own handler because `serveWrongMethod` hardcodes the edit URL's `GET, POST`.
- `GET /game/{system}/{id}/delete` — the page confirming that game's deletion: what will be erased named file by file, the two ways out (confirm, or cancel back to the game page), and a note when the game is protected. Sent with `Cache-Control: no-cache` — storable, so the list's scroll restoration survives, but revalidated, so going back after the deletion does not offer to delete the game again. Unknown game → `404` worded as possibly-already-deleted.
- `POST /game/{system}/{id}/delete` — deletes the game, then `303 See Other` to `/system/<system>?deleted=<name>&system=<system>[&warning=…]#deleted` — or to `/` with the same query when that game was the **last of its system**, since landing on a system that no longer exists would answer a 404 to a deletion that succeeded. Refusals: `403` cross-site (same `crossSite` check as the save), `400` for an unreadable body, `404` for an unknown game. A registry that could not be written re-renders the **confirmation page** with a page-level `Problem` rather than a bare `500` page, so the deletion can be retried from where it failed.
- `/game/{system}/{id}/delete` (methodless pattern) — any other method gets `405` with `Allow: GET, POST`. No `DELETE` verb is exposed: HTML forms without JS cannot send one, and it would be a second unauthenticated destructive entry point to keep in step.
- `/game/{system}/{id}/edit` (methodless pattern) — any other method gets `405` with `Allow: GET, POST`. The pattern has to be registered explicitly: the `/` catch-all matches every method, so the mux's own method-not-allowed handling would never fire for this URL.
- `GET /import` — the import flow's one page, rendering whichever of its five states holds: the other job holding the slot, no ROMs folder configured (a zero summary plus `config add-roms-folder`, no button), no run in flight (the briefing), a run in progress (auto-reloading, no button), and the report of the last run followed by the briefing again. `?quiet` renders any of them without the auto-reload. See "Importing the ROMs folders" below.
- `POST /import` — starts the import in a detached goroutine and answers `303 See Other` to `/import` itself. Same refusals as `POST /complete`.
- `/import` (methodless pattern) — any other method gets `405` with `Allow: GET, POST`, for the same reason as the edit URL's.
- `GET /complete` — the completion flow's one page, with the same five states and the same `?quiet`: the other job holding the slot, no ROMs folder configured (naming `config add-roms-folder`, offering no button), no run in flight (the confirmation), a run in progress, and the report of the last run followed by the confirmation again. See "Completing the ROMs folders" below.
- `POST /complete` — starts the completion in a detached goroutine and answers `303 See Other` to `/complete` itself. Refusals: `403` cross-site (same `crossSite` check as the save), `400` for an unreadable body or one over `maxFormBytes`. A submission arriving while either job is in flight, or with no ROMs folder configured, starts nothing and still redirects — there is no failure to report, only a state the page already words.
- `/complete` (methodless pattern) — any other method gets `405` with `Allow: GET, POST`, for the same reason as the edit URL's.
- `GET /media/` — the registry folder's media files, through `http.StripPrefix` + `http.FileServer` over `fileOnlyFS`. `http.Dir` confines every lookup to the registry folder (neutralizing path traversal), and `fileOnlyFS` additionally refuses directories, so the registry's arborescence is never listed.
- `/` (catch-all) — anything else, including a malformed game URL (`/game/`, `/game/<system>`, `/game/<system>/`, or an extra path segment), renders the themed 404 page naming what was not found, with a link back to the list.

## Rendering
Pages share one `layout` (theme, marquee header) that each template fills with its own `title`/`body` blocks; the stylesheet is `site.StyleSheet` (shared with the static site) plus this module's own `page.css` (breadcrumb, game page, metadata grid, confirmation page, not-found page). `render` executes a template into a buffer *before* writing anything, so a template failure surfaces as a clean 500 instead of a truncated page. Pages that render content never send `Cache-Control: no-store` — that directive would defeat the browser's scroll restoration when going back to the list; `renderProblem` does, since a `404` is cacheable by heuristic and the URLs answering one here are those whose game a later import may well recreate.

Game URLs are built by `gameURL` (each of system and id percent-encoded), system URLs by `systemURL` (likewise) — every "back to the system" affordance (breadcrumbs of the game/edit/delete pages, the game page's `back-to-top`, the deletion's landing page) goes through it rather than the `/#<system>` anchor it replaced. Media URLs are built by `mediaURL`, which prefixes `/media/` and **cleans** the path: `gamelist.xml` writes media references as `./images/foo.png`, and served as-is that non-canonical URL makes `http.FileServer` answer a redirect whose `Location` re-escapes the already-escaped path, sending the browser to a file that does not exist. The static site links the same media relatively, where the extra `./` is harmless — hence the cleaning lives here rather than in [`modules/site.md`](site.md).

## Correcting a game (backlog item 015)
`edit.go` holds the form's shape, `save.go` what happens when it is submitted. `editableFields` is the single table describing the eight controls (key, the registry field it corrects, label, kind, hint) — the "year" control corrects a `release_date`, which is why the two names are kept apart. `editValues` carries the values **as displayed** (a star count, a year); `displayedValues` reads a stored game into it, `storedMetadata` converts a submission back, leaving the stored rating and release date byte-identical when their displayed form did not change — see [`decisions/019`](../decisions/019-edit-the-displayed-formats-not-the-stored-ones.md). `editForm` builds the view for both the empty form and a refused submission, which is what makes the edit page its own URL — see [`decisions/018`](../decisions/018-metadata-editing-on-its-own-page-with-post-redirect-get.md).

The save takes the write lock for the whole operation, applies the correction to a `Clone()` of the snapshot, persists it through [`modules/store.md`](store.md), and only then swaps it in: a failed write leaves the served pages and the disk agreeing. A site-regeneration failure is not treated as a failed save — the registry is the source of truth, so the redirect happens anyway and the game page's banner says the consultation site is stale. Submitted values are trimmed and a textarea's CRLF line breaks normalized to LF, or a correction that changed nothing would rewrite the description and make every later import report the game as updated. Every constraint the form expresses (required name, year bounds, the rating's offered choices) is re-checked server-side, since a client is free to ignore them. With no accounts to authenticate on a home network, a submission whose `Sec-Fetch-Site`/`Origin` says it came from another site is refused outright.

## Correcting the ROM path (backlog item 021)
`rompath.go` holds the control's shape, the wording of every refusal, the composition of the confirmation, and the query the redirect carries. The path is deliberately **outside** `editableFields` — it identifies the entry rather than describing it — so `editPage.PathField` is its own `formControl`, rendered in its own fieldset before the metadata one, with no `Manual` key, no badge and no hand-back checkbox. It still reuses the `.field` markup and feeds the same `Errors` summary, so `#field-path` anchors like every other control: one error pattern, not two. `pathError` refuses in words (delegating to `pathRefusal` for whatever `registry.ValidatePath` names, then checking the registry for a duplicate); it is the one refusal needing the registry, which is why `validate` takes it as a parameter rather than computing it. The duplicate message names the game holding the identifier **only when that adds something** — a game called after its own file would otherwise be introduced twice in one sentence. It deliberately carries no link to that game: the message is rendered both in the field and inside the error summary, whose entries are already links, and an anchor nested in an anchor is invalid HTML.

`saveGame` applies the path **after** the metadata (`UpdateMetadata` addresses the entry by its old identifier), then follows [`decisions/024`](../decisions/024-the-rom-path-is-an-identity-renamed-write-first-erase-after.md): `store.Save` the candidate, swap the snapshot in, and only then `registry.RemoveGameFile` the old identifier's file — the reverse of a deletion's order. The swap is **not** conditioned on that erasure succeeding, or the served snapshot would contradict a disk that already holds the new state; a leftover file becomes a caveat naming it (`registry.EntryFileName`), never a `500`. A rename keeping the same identifier erases nothing and does not claim the page moved. The domain is still asked to refuse on its own terms even though `pathError` just checked the same rules — it owns them, and a rule added there must not slip through here silently.

Confirming a path change is the one outcome no table can hold: it names the path the user gave. `savedConfirmation` therefore reads the whole query rather than the outcome alone, and `pathConfirmation` composes the sentence from `path`, `moved` and `left`. `moved` is *stated* rather than recomputed, because the page landed on cannot know which address the user came from.

`formControl.DescribedBy` was added here and applied to every control: one carrying both a hint and an error must name both in `aria-describedby`, or a screen reader announces only the hint and the refusal goes unheard. The ROM path is the first control that always has a hint and can be refused — the metadata controls were fixed by the same change. `page.css` adds `.game__file` (under the title, `overflow-wrap: anywhere`, never a horizontal scroller), `.field__control--path` (monospaced, so a stray dot or double space is visible), and the same wrapping on `.field__hint`, `.field__error` and `.errors li`, which now carry paths.

## Protecting a whole game (backlog item 018)
`protect.go` holds both the control's shape and its handler. `protectionOf` turns an entry into the `protectionControl` the game page renders: one sentence stating the result (`Not protected …` / `Partly protected …` / `Protected …`) and the single control that state allows. A fully protected game offers the lift and **suppresses every per-field `hand-edited` badge** — the game-level sentence already says it, and six lit badges read as noise or as a contradiction. The partly protected state deliberately offers no bulk lift: in bulk it would discard which fields the user had corrected, which cannot be reconstructed, so selective hand-back stays on the edit form (see [`decisions/021`](../decisions/021-whole-game-protection-is-every-field-marked-at-once.md)). The state comes from `registry.Entry.FullyProtected` over all eight editable fields, not from the six rows the `<dl>` shows — otherwise a game whose only unprotected field is `desc` would wrongly read as protected.

`setProtection` reuses the save's whole sequence (write lock, `Clone()`, [`modules/store.md`](store.md), swap in only once the write succeeded, site-regeneration failure not treated as a failed change). Confirmations moved to a `savedConfirmations` table keyed by outcome, with `staleSuffix`/`staleCaveat` composing the stale variant, rather than one switch case per message; the sentences state the **resulting state** rather than the action, so they stay true when a stale page's submission turns out to be a no-op.

## Deleting a game (backlog item 016)
`delete.go` holds the confirmation's shape and both handlers. Confirming is its own page rather than a control on the game page — the UI ships no JavaScript, so there is no `confirm()` to lean on, and the flow reuses item 015's GET-form/POST-action shape (see [`decisions/018`](../decisions/018-metadata-editing-on-its-own-page-with-post-redirect-get.md)). `deletedFiles` lists what is **really** on disk, reusing `site.GroupBySystem`'s media-presence resolution — promising to delete four media a game never had would misrepresent what is at stake — and prefixes the JSON file with the system so every path in the list is relative to the same folder. `Protected` is `len(ManualFields) > 0`, not `FullyProtected()`: any hand-edited value is worth warning about before it is erased, and protection against *updates* deliberately does not block deletion.

`deleteGame` is the one change that does **not** follow the save's "swap the snapshot in only once the whole write succeeded" rule: `registry.Save` never deletes, so the deletion is already persisted when `registry.RemoveByID` erases the game's JSON, and the snapshot is swapped in right then. Deferring it would let the next write of any kind rewrite every entry of a stale snapshot and resurrect the deleted game's file. Consequently any later `store.Save` failure is a caveat on a `303`, never a `500` — see [`decisions/022`](../decisions/022-a-deletion-is-committed-when-the-game-file-is-gone.md). Only a JSON that could not be erased is a real failure, and it re-renders the confirmation page rather than a dead-end error page. The `crossSite` check is left exactly as strict as the edit form's — no fail-closed variant for the destructive route, since the edit form can overwrite a scraped description just as irrecoverably, and a stricter rule would refuse legitimate deletions from browsers sending neither `Sec-Fetch-Site` nor `Origin`.

The confirmation travels to the list as the game's **name** plus its system, not an opaque token like the save's: a list of several hundred games cannot show what left it, so a generic "Game deleted." would make the most likely error of this flow — deleting the wrong game — invisible. Caveats ride along as repeatable `warning` values (`media-left`, `stale-site`), composed onto the sentence by `deletedConfirmation`.

## The two background jobs (backlog items 022 and 023)
`job.go` holds everything the import and the completion share: the two URLs, the `jobKind` naming each, the `jobDescriptions` table (URL, the sentence a bystander page uses, and the count format owned by [`modules/registry.md`](registry.md)), the state machine, the page view, the `startJob` preamble, and the template partials. Neither flow's own file holds any of it twice.

**One slot for both** (see [`decisions/027`](../decisions/027-one-background-job-at-a-time-whichever-direction-it-goes.md)): `jobs.start(kind)` hands out a `*jobHandle` or nil, and `nil` covers both "that kind is already running" and "the other one is". The two flow in opposite directions over the same files, so left independent an import could read a `gamelist.xml` a completion is halfway through replacing. `jobs.view(kind)` returns the kind's own report **and** the other kind when it holds the slot, from a single lock — two reads could straddle a run ending and leave the page contradicting itself.

The `*jobHandle` is the only thing able to write into a run, which is what keeps the slot and the report in step; `progress` has exactly the signature the domain packages take as their callback, so it is passed as is. `jobs` guards itself with its own `sync.Mutex`, deliberately not `webUI.mu`: a run lasts minutes, and holding the snapshot lock that long would have Go's `RWMutex` queue every read behind the first correction submitted meanwhile. Both runs take `mu.RLock` only long enough to capture `ui.reg` and `ui.registryFolder`, then work against that pointer — safe because every change applies to a `Clone()` and swaps it in, leaving the captured one untouched (see [`decisions/025`](../decisions/025-completing-roms-folders-runs-in-the-background-behind-one-page.md)).

The slot is taken by `startJob` **before** the `303`, never inside the goroutine: a double click or a replayed submission arriving before the goroutine was scheduled would otherwise find it free and set two runs on the same files. `finish()` is deferred, so the slot is freed and the report closed whatever the run does. A report survives its run and stays readable until the next run of the same kind replaces it — these operations write with no way back, so their account has to outlive the browser tab.

`refreshSeconds` is concatenated into the partials' source rather than passed as data, so the `<meta http-equiv="refresh">` tag carries no dynamic value to escape; it sits in the `{{define "head"}}` filling the `{{block "head" .}}` added to `layout` for it. `jobPage.Refresh` is what gates it — a run in flight **and** no `?quiet` in the query. The report never reloads, or it would keep stealing focus from whoever reads it; and the running page states the interval in words and offers `quietParam` as a JS-free way out, without which a screen reader is reset every five seconds and never reaches the end of the folder list. `newJobPage` parses the partials under each flow's own template: `{{define "head"}}` cannot go into `newPage` itself, since every other page would then be asked for a `.Refresh` it does not have.

Counts are held positionally (`folderReport.Counts [3]int`) and worded by `summarize` through the kind's format, so no line of either page can drift from what the CLI prints; `jobReport.Totalled` suppresses the total when a single folder makes it the same sentence twice. `jobReport` keeps `Problem` (the run itself failed) apart from `Caveat` (it applied, with a reservation) — only the first counts as `Failed`.

## Completing the ROMs folders (backlog item 023)
`complete.go` holds what is specific to that direction: both handlers and the one template. It is the only route that writes **outside** the registry — into the user's Batocera folders — hence the confirmation page, modelled on the deletion's, naming every folder and saying the rewrite cannot be undone. `serveComplete` never writes; `startCompletion` does.

A folder that cannot be read **stops** the run — the ones already done keep their counts and the failing one is named with its error. That deliberately matches `scrape` rather than carrying on to the next folder: two entry points onto one domain operation may differ in what they offer, never in what they mean. The template renders neither `Problem` nor `Caveat`: this flow writes nothing the store commits, so nothing can set them.

## Importing the ROMs folders (backlog item 022)
`import.go` holds the opposite direction: both handlers, `commitImport`, the verdict, and the one template. Its page is a **briefing**, not a warning — it only reads the ROMs folders, and everything it writes the tool can rebuild from them — but it still names every folder and states the direction, since the verb alone does not.

`importRomsFolders` walks every folder into a `Clone()` of the captured snapshot and hands it to `commitImport`, which takes the write lock for the persist **and** the swap, exactly as `saveGame` does. Three outcomes are told apart there:
- the served snapshot is no longer the one captured → the run stands down, writing nothing, and says to run it again: the clone predates a correction saved meanwhile, and writing it out would erase a hand-typed value without a word (see [`decisions/029`](../decisions/029-an-import-stands-down-before-a-correction-saved-while-it-ran.md));
- `store.Save` failed outright → `fail`, and the snapshot is not swapped, so the served pages and the disk keep agreeing;
- only the site regeneration failed → `note`, and the swap happens: the registry is the source of truth and it holds the games.

A folder that cannot be read stops the run and **nothing is persisted at all**, matching `update`, which returns before saving. The counts the earlier folders reached are still reported, and the report says in words that nothing was written so they cannot be read as a claim (see [`decisions/028`](../decisions/028-an-interrupted-import-writes-nothing.md)).

`importVerdict` words the lead sentence from `jobReport.Totals`, because the commonest outcome of all — a repeat import finding nothing new — is a row of zeroes that reads as a breakdown if left to speak for itself. It tells apart "the registry was already up to date" (nothing added or updated, something unchanged) from "these folders held nothing to import" (all three zero). `importPage.ZeroSummary` covers the one state with counts but no run behind them: nothing configured to import from, which the acceptance criteria ask to show as a zero summary rather than as a refusal.

## Browsing on a phone (backlog item 020)
`system.go` holds the paginated system page: its view (`systemPage`), its handler, and the three helpers the paging rests on — `entriesOfSystem` (filter + the shared sort order), `requestedPage` (the `?page=` contract, including what makes it a 404), and `pageURL` (empty outside `[low, high]`, which is how the pager renders an edge's control as unavailable rather than dropping it and shifting under the thumb). The pager markup is one `{{define "pager"}}` rendered twice. `gameCards` is shared by nothing else yet but sits here because the system page is the only list of cards left; a `gameCard` carries the name, the description, the cover art and the link, and deliberately **not** the release year — the year is the game page's business, not the list's (backlog item 025).

Density is a *theme* concern, so it lives in [`modules/site.md`](site.md)'s shared stylesheet and applies to the static site too: below 640px the `.grid` becomes a bordered list and `.card` a 3.5rem row (square thumbnail and name, description hidden). `page.css` adds only what is specific to the served pages — `.systems` (the summary), `.pager`, `.button--disabled`, the `is-current` navigation pill — plus a 640px block giving every `.button` a 2.75rem minimum height. Verified at 390×844: no page scrolls horizontally, and every control (buttons, navigation pills) measures at least 44px.

**Architecture note:** the served UI navigates to real per-game pages instead of reproducing the static site's CSS-only `:target` overlay, and deliberately ships neither — see [`decisions/015`](../decisions/015-real-per-game-pages-in-the-served-web-ui.md); backlog item 017 (media management) builds its forms on those URLs, as items 015 and 016 already did. The not-found page was generalized into one themed `problem` page (`{Code, Title, Message}`) once refusals other than 404 appeared. Tests drive the handler through `net/http/httptest` without opening a port; the save is also covered by a concurrent read/write test meant to be run under `-race`.
