# A gamelist.xml is written beside the old one, then swapped in

**Context:** `gamelist.WriteFile` opened the target with `os.Create`, which truncates the file before a single byte of the new document is written. That file is the user's only copy, sits in their Batocera folders under no version control, and holds fields the registry never sees (favourites, `lastplayed`, `playcount`) that the rewrite reproduces from what was parsed. Backlog item 023 makes the web UI rewrite it from a detached goroutine (see [`025`](025-completing-roms-folders-runs-in-the-background-behind-one-page.md)), which the process can kill on shutdown mid-write.

**Decision:** The document is written to a temporary file created in the **same folder**, flushed to disk, then renamed over the target, inheriting the previous file's mode when there was one. A failure at any point removes the temporary file and leaves the original byte-identical.

**Consequence accepted:** what refuses the write is now the **folder**, not the file. A `gamelist.xml` left read-only is replaced all the same, since the rename only needs the folder — `chmod 444` is no longer a way to shield one from this tool. Batocera rewrites those files itself, so nobody was relying on that; the tool's own protection (`Entry.ManualFields`) is what shields values, and it acts before the file is ever written.

**Reason:** It is what makes a background run survivable: an interruption, a full disk or a panic can no longer leave a truncated `gamelist.xml`, only a stray temporary file next to an intact one. Doing it in the same folder is what makes the rename atomic — across filesystems it would degrade into a copy. The CLI's `scrape` gets the same guarantee for free, which is the point: the two entry points write the user's files the same way.

**Rejected alternatives:**
- *Keeping `os.Create` and relying on the confirmation page* — the confirmation guards against writing when the user did not mean to, not against the write being interrupted halfway.
- *Backing the old file up before rewriting* — leaves the user to decide what to do with the copies, and does not help the case where the interruption lands between the backup and the rewrite.
- *Waiting for the running completion before the server exits* — a nicety once the write is all-or-nothing, and it would have forced `webui.Handler` to return something other than an `http.Handler`.
- *Making the media copy atomic too* — a partially copied medium is regenerated by the next run and is not the file the user cannot afford to lose; left as it already behaves for `scrape`.
