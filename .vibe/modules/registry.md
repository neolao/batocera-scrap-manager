# Module: registry
**Role:** Centralized index of already-known games (scraped metadata and media), populated and kept up to date by importing the ROMs folders' `gamelist.xml` files without duplicating known entries, while detecting metadata that changed and copying the referenced media.
**Files:** `internal/registry/registry.go`, `internal/registry/metadata.go`, `internal/registry/rompath.go`
**Exports:**
- `registry.Entry{System, Game, ManualFields}` — `ManualFields` names the metadata fields corrected by hand (see `editableFields` in `metadata.go`), which an import must not overwrite — see [`decisions/017`](../decisions/017-protect-hand-edited-fields-from-later-imports.md)
- `registry.Registry{Entries}`
- `(*Registry).Clone() *Registry` — a copy whose entries can be modified without touching the original, for a caller that applies a change, tries to persist it, and only swaps it in once the write succeeded (used by [`modules/webui.md`](webui.md)'s save)
- `registry.Load(path string) (*Registry, error)` — path is the registry folder; reconstructs the registry by scanning its per-system subfolders for game JSON files; missing folder = empty registry, no error
- `registry.Save(path string, reg *Registry) error` — writes one JSON file per game (named after the ROM's base name, extension stripped) inside its system's subfolder, creating folders as needed
- `(*Registry).Import(system string, games []gamelist.Game) (added, updated, unchanged int)` — deduplicated by (system, gameID) key, via `indexOf` (matches on `gameID(Game.Path)` — base name, directory prefix *and file extension* both stripped — see [`decisions/005`](../decisions/005-match-registry-entries-by-rom-filename-not-full-path.md) and [`decisions/014`](../decisions/014-dedupe-by-extension-stripped-filename-too.md)); if the entry already exists, compares the full metadata and replaces + counts "updated" on a difference, otherwise "unchanged"
- `registry.ImportFromRomsFolder(reg *Registry, romsFolder, registryFolder string, onProgress func(ProgressEvent)) (added, updated, unchanged int, err error)` — scans the subfolders (one per Batocera system) of a ROMs folder, reads `gamelist.xml` if present (otherwise silently skips the system), imports each game, and for every added or updated game copies its referenced media (cover art, video, marquee, thumbnail) into `registryFolder`, mirroring the Batocera per-system arborescence; unchanged games are not recopied. A game with neither a description nor an image (`hasScrapedData`) is skipped entirely — not imported, not counted, no progress event — since it carries no scraped information worth keeping (see [`decisions/007`](../decisions/007-skip-empty-games-only-on-import-not-retroactively.md)); this only affects new imports, an already-known entry is never removed retroactively if its local sheet later loses its last data. If non-nil, `onProgress` is called once per game actually imported (added, updated, or unchanged) with its system, 1-based index and total count within that system's full local game list (including skipped games), and name
- `registry.ProgressEvent{System, GameIndex, GameCount, GameName}` — one progress notification emitted by `ImportFromRomsFolder` and `ImportGame`. `CompletionEvent` (below) is a type alias for `ProgressEvent`, not a separate struct — both flows describe the same shape (a game's position within its system's local game list)
- `registry.ImportGame(reg *Registry, romsFolder, registryFolder, system, romFilename string, onProgress func(ProgressEvent)) (added, updated, unchanged int, err error)` — the single-game counterpart of `ImportFromRomsFolder`: imports the one local game entry matching (system, romFilename) — matched by ROM base name via the same rule as `indexOf` — from `romsFolder`'s local `gamelist.xml`, then copies its media if newly added or changed. Returns `registry.ErrGameNotFound` if the game has no entry in the system's local `gamelist.xml`. A game with neither a description nor an image is silently skipped, exactly like `ImportFromRomsFolder` (see [`decisions/007`](../decisions/007-skip-empty-games-only-on-import-not-retroactively.md)) — not an error. Unlike `CompleteGame`, a media copy failure is propagated as a real error (mirroring `ImportFromRomsFolder`'s own behavior) rather than counted as a soft per-game failure. `onProgress`, if non-nil, fires once, only if the game was actually imported (added, updated, or unchanged) — see [`decisions/013`](../decisions/013-target-single-game-by-real-disk-path.md)
- `registry.CompleteRomsFolder(reg *Registry, romsFolder, registryFolder string, onProgress func(CompletionEvent)) (processed, completed, failed int, err error)` — the reverse flow: for each system's local `gamelist.xml` in `romsFolder`, fills any field left empty in a local game entry from the matching registry entry (same system + ROM filename, via `indexOf`), never overwriting a field already set locally; for every newly filled media reference, copies the file from `registryFolder` into `romsFolder`. A game with no matching registry entry, or already fully complete, is left untouched (not counted as completed, no event). A media copy error counts that game as failed but does not abort the run; the local `gamelist.xml` is rewritten once per system (via `gamelist.WriteFile`) if any of its games changed. If non-nil, `onProgress` is called only for games that actually had a field filled (whether or not their media copy then succeeded) — untouched games produce no event
- `registry.CompletionEvent` — alias of `ProgressEvent`; one progress notification emitted by `CompleteRomsFolder` and `CompleteGame`
- `registry.CompleteGame(reg *Registry, romsFolder, registryFolder, system, romFilename string, onProgress func(CompletionEvent)) (completed, failed bool, err error)` — the single-game counterpart of `CompleteRomsFolder`: fills the gaps of the one local game entry matching (system, romFilename) — matched by ROM base name via `indexOf`, same as every other registry lookup — from the matching registry entry, then copies any newly filled media reference. Returns `registry.ErrGameNotFound` (reusing the same sentinel as `Remove`) if the game has no entry in the system's local `gamelist.xml`, or no matching entry exists in `reg`; `completed` reports whether a field was actually filled, `failed` whether the subsequent media copy failed (the local `gamelist.xml` is still rewritten with the filled fields in that case). `onProgress`, if non-nil, fires once, only when a field was filled — see [`decisions/013`](../decisions/013-target-single-game-by-real-disk-path.md)
- `registry.Remove(reg *Registry, registryFolder, system, romFilename string) error` — `RemoveByID` for the game ID derived from `romFilename` through `GameID`, so a full path also works (only its base name matters) and a bare filename (e.g. `Sonic.zip`) suffices even if the ROM originally lived in a subfolder
- `registry.RemoveByID(reg *Registry, registryFolder, system, id string) error` — deletes the metadata JSON file and every referenced media file (cover art, video, marquee, thumbnail) of the entry of `system` whose `GameID` is `id`, then removes that entry from `reg`. Located via the shared `indexOfID`, like `FindByID`: callers that already hold an identifier must not run it through `GameID` again, which would truncate an id containing a dot and either miss the entry or match a different one. Returns `ErrGameNotFound`, deleting nothing, if no entry matches. A file already absent is success, not an error.
  The JSON file is deleted **first**, and that deletion is the commit point: once it is gone the entry leaves `reg` even if a medium resists, and the remaining media are still attempted rather than abandoned at the first failure — reported together as `ErrMediaLeftBehind`. The reverse order would leave a listed game with broken images. A media reference resolving outside `<registryFolder>/<system>` (`mediumPath`) is left alone rather than followed, since scraped data is what fills those references and `os.Remove` has no undo — see [`decisions/022`](../decisions/022-a-deletion-is-committed-when-the-game-file-is-gone.md)
- `registry.GameID(path string) string` — the identifier of a game inside the registry: its ROM path's base name, without directory prefix or file extension. The single source of that rule, used to name the JSON file on disk (`gameFileName`), to deduplicate entries (`indexOf`), and to address a game from outside the package (`FindByID`, and hence the web UI's per-game URLs) — never re-derived independently, see [`decisions/014`](../decisions/014-dedupe-by-extension-stripped-filename-too.md)
- `(*Registry).FindByID(system, id string) (Entry, bool)` — looks up the entry of `system` whose `GameID` is `id`, for callers addressing a game by identifier rather than by ROM path. Unlike `indexOf` it does not run `id` through `GameID` again (via the shared `indexOfID`), which would truncate an id whose game name contains a dot (e.g. `Micro Machines v3.0`) and lose the entry
- `registry.Metadata{Name, Desc, Rating, ReleaseDate, Developer, Publisher, Genre, Players}` — the metadata of a game as a user corrects it: every editable field at once, an empty one meaning "cleared". The ROM path and the media references are deliberately absent, so no correction can reach them
- `registry.UpdateMetadata(reg *Registry, system, id string, m Metadata, handBack []string) error` — replaces the editable metadata of the entry of `system` whose `GameID` is `id` (located via the shared `indexOfID`, like `FindByID`), and marks as hand-edited (`Entry.ManualFields`) every field the correction actually changed; a field named in `handBack` is unmarked instead, its submitted value still stored. Returns `ErrGameNotFound`, without modifying anything, if no entry matches. Marks are recomputed into a fresh slice, so an entry cloned from another never writes through to it
- `registry.Protect(reg *Registry, system, id string) error` / `registry.Unprotect(reg *Registry, system, id string) error` — the whole-game counterpart of `UpdateMetadata`'s per-field marking (located via the same `indexOfID`): `Protect` sets `Entry.ManualFields` to every name in `editableFields`, `Unprotect` clears it — including the marks left by earlier per-field corrections, since lifting is a whole-game statement too. Neither writes a game value: protecting states that the stored ones are right. Both return `ErrGameNotFound` without modifying anything if no entry matches, and both assign a fresh slice, so applying either to a `Clone()` never writes through to the original — see [`decisions/021`](../decisions/021-whole-game-protection-is-every-field-marked-at-once.md)
- `(Entry).FullyProtected() bool` — whether every editable field is marked, which is what `Protect` leaves behind. Derived from the `editableFields` table rather than stored, so no caller holds its own idea of what a protected game is; order-independent and indifferent to a mark naming something uneditable
- `registry.ChangePath(reg *Registry, system, id, newPath string) error` — stores `newPath` as the ROM path of the entry of `system` whose `GameID` is `id`, which moves it under the identifier `newPath` derives — and with it the JSON file naming it on disk and the URL addressing it. The path is stored **exactly as given** (cleaning it would rewrite a value the user did not change). In-memory only: it touches no file, so it composes with the `Clone()`/[`modules/store.md`](store.md)/swap sequence the web UI's save already follows. It marks nothing as hand-edited — the path identifies the entry rather than describing it, and is absent from `editableFields` by design (see [`decisions/024`](../decisions/024-the-rom-path-is-an-identity-renamed-write-first-erase-after.md)). Returns `ErrGameNotFound`, `ErrDuplicateGameID`, or whatever `ValidatePath` refuses — in every case without modifying anything. The duplicate check compares the matched **index**, not the identifier: an entry whose path changes without changing its identifier (a new subfolder, another extension) holds that identifier itself and would otherwise be refused as a duplicate of itself
- `registry.ValidatePath(romPath string) error` — reports whether a path is storable, naming the rule it breaks. Exported so a caller can refuse a submission with its own wording before building the candidate registry. Refuses: blank; absolute; escaping the system folder through `..` (tested on `path.Clean`'s result); a backslash (a separator on Windows, an ordinary character elsewhere — the stored form must not depend on the host OS); a control character; a last segment of `""`, `.` or `..` (read **before** cleaning, since `Clean` turns `disc1/`, `disc1/.` and `disc1/..` back into an ordinary `disc1`); a derived `GameID` that is empty, `.` or `..`; and an identifier whose file name would exceed 255 bytes
- `registry.RemoveGameFile(registryFolder, system, id string) error` — deletes the metadata JSON the entry of `system` was stored under while its game ID was `id`, and **nothing else** — no media, unlike `RemoveByID`: a rename never moves the files a game's media references name. It is what keeps a rename from leaving a duplicate behind, since `Save` only ever writes files. A file already absent is the wanted state; an `id` that is not a plain base name (empty, `.`, `..`, or carrying a separator) is refused with `ErrUnusablePath` rather than followed
- `registry.EntryFileName(id string) string` — names the JSON file an entry of the given game ID is stored under. The single place that rule lives, so `gameFileName` (which derives the id from a game's path) and a caller already holding an id cannot drift apart — the drift [`decisions/014`](../decisions/014-dedupe-by-extension-stripped-filename-too.md) was written about. Exported for the sake of a caller **naming** that file to the user, never to build a path to it
- `registry.ErrEmptyPath` / `ErrAbsolutePath` / `ErrEscapingPath` / `ErrUnusablePath` — the reasons `ValidatePath` refuses a path, told apart because a caller shows one message per reason: a single "invalid path" would leave the user guessing which rule was broken
- `registry.ErrDuplicateGameID` — sentinel marking a path whose identifier already belongs to another game of the same system. Two entries sharing one identifier would collide on the same JSON file, and `Save` would silently keep only the last one written
- `registry.ErrGameNotFound` — sentinel error returned by `Remove`, `RemoveByID`, `UpdateMetadata`, `Protect`, `Unprotect` and `ChangePath` when no entry matches
- `registry.ErrMediaLeftBehind` — sentinel marking the half-outcome of a deletion worth telling apart: the game's JSON file is gone from disk and its entry from `reg`, but at least one media file could not be deleted (wrapped with their names). A caller reporting it as a failure would claim nothing was deleted while the game is really gone; the CLI turns it into a `warning:` line with exit code 0, the web UI into a caveat on its confirmation

**Depends on:** [`modules/gamelist.md`](gamelist.md)

**Hand-edited fields:** `editableFields` (`metadata.go`) is the single table of the eight metadata fields a user may correct — name, desc, rating, release_date, developer, publisher, genre, players — pairing each with its accessor and with the name it is stored under; media and the ROM path are absent from it by design, so nothing can protect or overwrite them through this path. `mergeGameEntry` calls `keepHandEditedFields` before comparing, so an import applies the incoming game then puts the protected values back: when they are the only difference the entry ends up identical and the game counts as **unchanged**, not updated on every run. A mark naming a field that is not editable metadata (a `path`, a media field, or one written by a later version) is simply ignored.

**Registry folder layout:** `<registryFolder>/<system>/<romBaseName>.json` holds one game's metadata, alongside `<registryFolder>/<system>/...` media subfolders (e.g. `images/`, `videos/`) mirroring the corresponding ROMs system folder — since media paths in `gamelist.xml` are relative to the system folder and are preserved unchanged when copied. There is no single index file for the whole registry: each game's entry is self-contained in its own file, so a corrupted or malformed entry only affects that one game on load. The file's shape is `storedGame`: the game's own fields flat at its root (unchanged), plus an optional `manual_fields` array listing the hand-edited ones — omitted entirely for a game nobody corrected, so files written before that feature, and files written now for untouched games, are identical and load with nothing protected.

**Architecture note:** `ImportFromRomsFolder` is exposed via the `update` CLI command (see [`modules/cli.md`](cli.md)), implemented for backlog item 002. Media copying was added afterward, reversing the initial decision to keep the registry metadata-only, once the need to keep the registry self-contained (independent of the original ROMs folders) was confirmed. The registry was then further split from a single index file into one file per game, for the same self-containment reason. `CompleteRomsFolder` was added for backlog item 003 as the reverse of `ImportFromRomsFolder`: the registry is read-only there, and ROMs folders are the ones written to — see [`decisions/004`](../decisions/004-registry-as-source-to-complete-roms-folders.md). `Remove` was added for backlog item 005, identifying the game to delete the same way every other registry operation does: by (system, ROM filename). Designing `Remove` surfaced an inconsistency between `indexOf` (which compared the full `Game.Path`) and on-disk storage (`gameFileName`, always flat per system, discarding any subfolder prefix) — `indexOf` was changed to match on filename alone, closing a silent-collision gap and letting `remove` take a bare filename instead of a full path — see [`decisions/005`](../decisions/005-match-registry-entries-by-rom-filename-not-full-path.md). `CompleteGame` was added for backlog item 011 to target a single game instead of a whole ROMs folder, reusing `mergeGame`, `copyFilledMedia`, and `indexOf` rather than duplicating `CompleteRomsFolder`'s logic; unlike the batch flow, a missing local entry or missing registry match is reported as `ErrGameNotFound` instead of being silently skipped, since the caller explicitly asked for that one game. `ImportGame` was added symmetrically for backlog item 012 (single-game `update`), reusing `mergeGameEntry`, `copyGameMedia`, and `hasScrapedData` rather than duplicating `ImportFromRomsFolder`'s logic; it keeps `ImportFromRomsFolder`'s existing skip-empty-game business rule as-is (silent skip, not an error) since that rule was already scoped to import as a whole, not just the batch entry point.

**Architecture note (backlog item 018):** `Protect`/`Unprotect`/`FullyProtected` were added so a game that is simply already right can be shielded without editing each of its values into something else and back. They are the existing marking at its limit rather than a second mechanism — no `Protected` flag on the entry, no change to the on-disk shape — which is what keeps the CLI and the web UI from disagreeing about what "protected" means; the state being derived from `editableFields` also means adding an editable field later cannot leave a game half-protected while still reading as protected. Media references stay outside it, so a protected game still follows its artwork when the ROMs folder points somewhere else (pinned by `TestProtect_ThenImportingAGameWhoseMediaMoved_StillRefreshesTheMedia`).

**Architecture note (backlog item 021):** `ChangePath`/`ValidatePath`/`RemoveGameFile` (`rompath.go`) were added so the ROM path — the one thing identifying an entry — can be corrected without editing a file by hand. They sit in their own file rather than in `metadata.go` precisely because the path is *not* metadata: adding it to `editableFields` would have given an identity the mechanics of a value, silently unprotected every already-protected game (`FullyProtected` iterates that same table), and left a `path` mark that `markedFields` would drop on the next correction anyway. The split of responsibilities is deliberate: `ChangePath` decides, `Save` writes, `RemoveGameFile` erases — so the caller can order the three the way [`decisions/024`](../decisions/024-the-rom-path-is-an-identity-renamed-write-first-erase-after.md) requires (write the new file, erase the old one after), which is the **reverse** of a deletion's order ([`decisions/022`](../decisions/022-a-deletion-is-committed-when-the-game-file-is-gone.md)): erasing first and then failing the write would destroy the only copy of the scraped metadata, while erasing last can only leave a recoverable duplicate. Two consequences are knowingly left standing: `Path` is not protectable, so a later import from a `gamelist.xml` still holding the old path overwrites the correction (same identifier) or adds a second entry beside it (changed identifier); and on a case-insensitive registry folder a rename differing only by case passes the duplicate check.

**Architecture note (backlog item 015):** `Metadata`/`UpdateMetadata` were added as the domain side of correcting a game from the web UI, alongside the hand-edit protection that makes such a correction survive the next `update` — see [`decisions/017`](../decisions/017-protect-hand-edited-fields-from-later-imports.md). `Clone` exists so the caller can persist a candidate registry before committing it in memory; nothing in this package depends on that ordering, but it is what lets a failed write leave memory and disk agreeing.

A second `/vibe:review` pass (2026-07-02) fixed a real bug found by `review-tests`: `gameFileName` stripped the ROM's file extension when naming a game's JSON file, but `indexOf` still matched on the full filename including extension, so two ROMs differing only by extension (e.g. `Sonic.zip` and `Sonic.iso`) collided on the same on-disk file with no warning — see [`decisions/014`](../decisions/014-dedupe-by-extension-stripped-filename-too.md). Both now derive their key from a shared `gameID(path string) string` helper. That same pass also: renamed the unexported `importGame` method to `mergeGameEntry` and the unexported `completeOneGame` helper to `fillGameFromRegistry`, so they no longer differ from the exported `ImportGame`/`CompleteGame` functions by capitalization alone; extracted `importSystemGames` and `completeSystemGames` from `ImportFromRomsFolder`/`CompleteRomsFolder`'s inner per-system loops (mirroring the earlier `importOneGame`/`fillGameFromRegistry`/`findGameByFilename`/`loadSystemEntries` extractions from the first pass); unified `CompletionEvent` as a type alias of `ProgressEvent` (the two were structurally identical); and introduced a `mediaFields` table (accessors for Image/Video/Marquee/Thumbnail) so `Remove`, `copyGameMedia`, and `copyFilledMedia` iterate one shared list instead of each hardcoding the same four fields separately.
